ZLAN 7110M – VirCom Documentation

Part 1: detailed documentation of the ZLAN 7110M device configuration in the VirCom software.

This part covers only the configuration in VirCom: the main Device Settings window, the More Advanced Settings window, the Firmware/Config section, the meaning of the Webpage directory in local PC field, the meaning of the Download and Bind ID buttons, and a detailed explanation of Modbus cfg.

Project context: The ZLAN 7110M is used here as a Modbus TCP ↔ Modbus RTU gateway. On the network side it communicates via TCP/IP; on the sensor side it communicates via RS485 with a Modbus RTU sensor.

1. Role of the ZLAN 7110M in the project

The VirCom software is used to configure the ZLAN 7110M device. In this project, the ZLAN serves two roles simultaneously:

  • on one side it appears on the network as a TCP server to which a client connects, for example QModMaster,
  • on the other side it communicates with the sensor via RS485 / Modbus RTU.

In other words: the ZLAN is a translator between the network world and serial RS485 communication.

QModMaster  --(Modbus TCP)-->  ZLAN 7110M  --(Modbus RTU / RS485)-->  Sensor
Important: Two different layers are therefore configured in VirCom: Network for network communication and Serial for RS485 communication with the sensor.

2. Main Device Settings window

VirCom – main Device Settings window. This is where device identity, network communication, and serial communication with the sensor are configured.

The Device Settings window is the basic device configuration window. It is divided into several sections: Device Info, Network, Serial, Function of the device, and Advanced Settings.

2.1 Device Info

The Device Info section contains device identification data. These items are usually not changed but are used to confirm that you are working with the correct ZLAN unit.

2.2 Network

The Network section configures the network behaviour of the device. This is the part that determines how QModMaster or another client will connect to the ZLAN over the network.

Why this setting was chosen: the goal was for QModMaster to connect to the ZLAN as a network device. The ZLAN must therefore have a valid IP address on the network and must be in TCP Server mode.

2.3 Serial

The Serial section determines how the ZLAN communicates with the sensor over RS485. This setting must match the sensor's parameters.

FieldFinal settingMeaning and why it is set this way
Baud Rate9600Serial communication speed. A direct RTU test of the sensor confirmed that the sensor responds correctly at 9600 baud.
Data Bits8Number of data bits in a transmitted frame.
ParityNoneNo parity bit is used. Any other setting would result in a corrupted or invalid response.
Stop Bits1Number of stop bits in the frame.
Flow ControlNoneFlow control is not used with this RS485 Modbus RTU communication.

The final verified serial setting was:

9600, 8, None, 1
Important: If the serial setting in the ZLAN does not match the sensor's serial setting, network communication may work but errors such as Timeout or Invalid data will occur on the RS485 side.

2.4 Function of the device

In the left part of the main window there are device function options. The critical option for this project is:

  • Modbus TCP To RTU

This option tells the ZLAN to translate incoming Modbus TCP requests from the network into Modbus RTU requests directed at the sensor on RS485.

Without this option: the ZLAN can communicate over the network and over RS485, but it cannot act as a Modbus gateway between the two worlds.

4. Firmware/Config

VirCom – Firmware/Config window. This is where the working directory for local files, device identification, and the Download button for sending the configuration to the ZLAN are found.

The Firmware/Config window is used to prepare and upload the configuration to the device. This is where the Webpage directory in local PC field, the Download button, and identification via DevID and Bind ID are used.

4.1 Webpage directory in local PC

The Webpage directory in local PC field specifies the local folder on the computer that VirCom uses as a working directory for creating helper configuration files before sending them to the ZLAN.

In practice this means VirCom first prepares local files in the specified folder and only then sends them to the device.

FieldExampleMeaning
Webpage directory in local PCC:\Apps\VirConAn existing folder on the disk where VirCom can write its helper files.
What happened when it was not set correctly: when the folder did not exist or was set to an invalid path, VirCom displayed the error:
The root directory of the local web page does not exist!

This error did not indicate a problem with Modbus communication, but rather that VirCom had nowhere to create its local working files. The fix was simple: create an existing folder on the disk and set it in this field.

4.2 DevID and Bind ID

DevID is the unique identifier of the physical ZLAN device. The Bind ID button is used to bind the prepared configuration to a specific hardware unit.

This is especially important when there are multiple devices of the same type on the network. Bind ID helps ensure that the configuration is not accidentally sent to the wrong device.

FieldMeaning
DevIDUnique identifier of the specific ZLAN device.
Bind IDBinds the configuration to a specific DevID so VirCom knows which device to transfer data to.

4.3 Download

The Download button in this window means sending the prepared configuration from the PC to the ZLAN device.

This is not a "download" in the internet sense. The flow is reversed: VirCom prepares the configuration files locally on the PC and then pushes them to the ZLAN when the button is pressed.

After a successful transfer the following message appeared:

Transfer complete. DON'T power down when LINK led light is blinking!

This means the transfer completed, but the device may still be writing data to internal memory. Do not power off the device while the LINK LED is blinking rapidly.

5. Modbus cfg

VirCom – Modbus cfg. This is where you specify which RTU register from the sensor is to be cyclically read and to which TCP register the ZLAN should map it.

The Modbus cfg section is critical for the mapping between the sensor world and the TCP client world. Here you configure which register the ZLAN should read from the sensor and which TCP register it should store it in.

5.1 Final settings used in the project

Command No        = 1
Slave Address     = 1
Modbus Function   = 4
Register Addr     = 3
Register Length   = 1
RTU Query Interval= 100 ms
RTU Reply Timeout = 500 ms
Modbus TCP Reg Addr = 0

5.2 Meaning of each field

FieldMeaningWhy it was set this way
Command NoSequential number of the rule in the table.Serves only as a record identifier. With one sensor, 1 is sufficient.
Slave AddressModbus address of the sensor on the RS485 bus.A direct RTU test confirmed that the sensor responds at address 1.
Modbus FunctionType of Modbus operation the ZLAN will perform towards the sensor.Testing showed that the light value is accessible via Function 04 – Read Input Registers.
Register AddrRTU register number in the sensor from which to read the value.Comparing light and dark confirmed that the value changes in register 3.
Register LengthNumber of registers to read.1 is sufficient because the light value is in a single register.
RTU Query IntervalHow often the ZLAN will poll the sensor.100 ms means frequent updates. For better stability this can be increased to e.g. 1000 ms.
RTU Reply TimeoutMaximum time to wait for a sensor response.500 ms is a reasonable value – long enough for a response but not unnecessarily large.
Support 05/06 cmdSupport for write commands.Not needed for reading light values, so it was left disabled.
Device off line, set register valueFallback value when the device is offline.Typically left at 0 to indicate that the sensor is not responding.
Modbus TCP Reg AddrTCP register number on the ZLAN side where the read RTU value is stored.The value from the sensor's register 3 was mapped to TCP register 0 so that clients can read it easily.

5.3 Mapping logic

After this configuration, the mapping works as follows:

Sensor RTU side:
Slave 1, Function 04, Register 3  -->  light value

ZLAN TCP side:
Register 0  -->  the same light value

This means a network client does not need to know that the sensor has its value in RTU register 3. It only needs to know that it should read register 0 from the ZLAN via TCP.

6. Brief summary of this part

In VirCom the ZLAN 7110M needed to be configured so that:

  • it is accessible on the local network via its own IP address and TCP port,
  • it communicates with the sensor over RS485 at serial setting 9600, 8, None, 1,
  • the Modbus TCP To RTU function is enabled,
  • the advanced settings use the Simple Modbus TCP to RTU mode,
  • the correct working directory is set in the Webpage directory in local PC field,
  • and the Modbus cfg section maps RTU register 3 to TCP register 0.
Result: after this configuration, the ZLAN 7110M can read the sensor over RS485 and make the light value available to a network client via Modbus TCP.

7. Configuration upload procedure

After configuring all parameters in VirCom, the configuration must be uploaded to the ZLAN device. This process consists of two main steps: Bind ID and Download.

7.1 Step 1 – check the device

  • verify the correct IP address of the device,
  • verify that you are connected to the correct ZLAN (especially if you have more than one),
  • check the DevID in Device Info.

7.2 Step 2 – Bind ID

The Bind ID button is used to bind the current configuration to a specific device. This ensures the configuration will be sent to the correct ZLAN unit.

Bind ID is not technically mandatory, but it is strongly recommended, especially if you have multiple devices on the network.

7.3 Step 3 – Download

After binding the configuration, press the Download button. This sends the configuration from the PC to the ZLAN device.

After a successful transfer the following message appears: 

Transfer complete. DON'T power down when LINK led light is blinking!

While the LED is blinking, the device is writing the configuration to memory and must not be powered off.

7.4 Recommended procedure

1. Check the device (IP, DevID)
2. Click Bind ID
3. Click Download
This procedure ensures the configuration is uploaded correctly and to the correct device.

Part 2 – QModMaster Configuration

QModMaster is used in this project to verify communication and to read values from the ZLAN 7110M device. On the QModMaster side the communication is Modbus TCP, and the ZLAN then internally translates the request to Modbus RTU towards the sensor.

Final working settings in QModMaster: Modbus Mode = TCP, Slave Addr = 1, Function Code = 04, Start Address = 0, Number of Registers = 1, ZLAN IP address and port 4196.

2.1 Opening the Modbus TCP settings

Open Options → Modbus TCP in the menu. This is where the network connection between QModMaster and the ZLAN device is configured.

QModMaster – Modbus TCP Settings window. This is where the ZLAN IP address and TCP port on which the ZLAN listens for Modbus TCP requests are configured.
FieldValueMeaning and why it is set this way
Slave IPe.g. 192.168.50.129IP address of the ZLAN device on the local network. QModMaster connects to this address.
TCP Port4196Port set in VirCom under Network → Port. Must be the same in both the ZLAN and QModMaster.

After filling in these parameters, confirm with the OK button.

2.2 QModMaster main window

The main QModMaster window is used for the actual data reading. Here you configure the Modbus operation type, register address, and number of registers to read.

QModMaster – main GUI with the final working settings. The program is in TCP mode and reads register 0 from the ZLAN.
FieldFinal settingMeaning and why it is set this way
Modbus ModeTCPQModMaster communicates with the ZLAN over the network. This must be TCP, not RTU, because the client connects to the ZLAN's IP address.
Slave Addr1Modbus device identifier. Address 1 is used in this project.
Scan Rate (ms)1000Periodic polling interval. 1000 ms means QModMaster reads the register once per second.
Function CodeRead Input Registers (0x04)Reads input registers. A direct RTU test confirmed that the sensor returns the light value via function 04.
Start Address0On the TCP side, register 0 is read because the ZLAN Modbus cfg maps the sensor's RTU register 3 to TCP register 0.
Number of Registers1Reading one register is sufficient to obtain the current light value.
Data FormatDecThe value is displayed in decimal, which is most practical for direct lux readings.
SigneddisabledThe light value is non-negative, so signed interpretation is not used.

In the example shown, QModMaster returns the value 20068. This means the client successfully read the value from the ZLAN, and this value corresponds to the current illumination measured by the sensor.

Important mapping logic:
The sensor physically communicates via RTU and its light value is in its register 3 at Function 04.
The ZLAN periodically reads this value and stores it in its TCP register 0.
QModMaster therefore does not read register 3, but reads only register 0 on the TCP side.

2.3 Bus Monitor

The Bus Monitor window is very useful for diagnostics. It displays outgoing requests (Tx) and incoming responses (Rx) in hexadecimal format.

QModMaster – Bus Monitor. Connection to the ZLAN and subsequent Modbus TCP requests and responses are visible.

What is visible in Bus Monitor

The log first shows a line about the successful connection: 

Connecting to IP: 192.168.50.129:4196 OK

This means the TCP connection between QModMaster and the ZLAN was successfully established.

Then the Modbus TCP frames are displayed: 

[TCP]->Tx ...
[TCP]->Rx ...

Meaning:

  • Tx – request sent by QModMaster to the ZLAN,
  • Rx – response returned by the ZLAN to the client.

The response contains a pair of data bytes. In the example the response is: 

01 04 02 4E 64

The part 4E 64 is the register value in hexadecimal. Converting to decimal gives the value 20068, which is also visible in the main window.

2.4 How this configuration was arrived at

QModMaster was first used in RTU mode via a USB-RS485 converter to verify:

  • the correct serial settings of the sensor,
  • the correct sensor address,
  • the correct function code,
  • and the correct register where the light value changes.

This RTU test confirmed: 

Slave Address = 1
Function Code = 04
RTU Register = 3
Serial = 9600, 8, None, 1

Once these parameters were known, the ZLAN was configured in VirCom to map RTU register 3 to TCP register 0, and QModMaster was switched to TCP mode to read register 0 directly from the ZLAN. This is the working configuration documented in this guide.
