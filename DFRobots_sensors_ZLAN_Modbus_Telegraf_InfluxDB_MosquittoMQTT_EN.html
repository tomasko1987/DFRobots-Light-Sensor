DFRobots Sensors → ZLAN → Modbus → Telegraf → InfluxDB, Mosquitto MQTT

This documentation combines the original guide to creating a Docker container for Telegraf and newer documentation on connecting two ZLAN devices with RS485 DFRobot light sensors. It is assembled as a practical step-by-step working guide.

Current system goal:
Two DFRobot SEN0644 light sensors are connected via RS485 to two ZLAN converters. ZLAN devices convert the communication to Modbus TCP. Telegraf running in a Docker container reads these values, publishes them to the MQTT Mosquitto broker at 192.168.50.103:1883 and can simultaneously store them in InfluxDB at 192.168.50.103:8086.

1. System architecture and visual diagram

The data path is:

DFRobot SEN0644 → RS485 → ZLAN 7110M → Modbus TCP → Telegraf Docker container → MQTT Mosquitto + InfluxDB
Diagram note: Telegraf now has two outputs simultaneously: it publishes current values to Mosquitto MQTT and simultaneously writes time-series data to InfluxDB, where they are stored in the bucket Roof_Light_Sensors.

2. Basic concepts

2.1 Docker container

A Docker container is an isolated environment in which a specific application runs. In this project, the Telegraf application runs in the container. A container can use its own files as well as files from the host system via volume mapping.

2.2 The /etc directory

/etc is the standard location for program configuration files in Linux. Telegraf inside the container expects its configuration typically here: 

/etc/telegraf/telegraf.conf

2.3 The /opt directory

/opt is often used for custom applications, helper files, or project configurations. In this case we have the configuration file on the host: 

/opt/telegraf/telegraf.conf

2.4 Host file vs. container file

When starting the container, we mapped the host file into the container. This means Telegraf inside the container reads /etc/telegraf/telegraf.conf, but it is actually the file from the host: /opt/telegraf/telegraf.conf.

Advantage: when the container is deleted, the external configuration file on the host is not deleted.

3. Creating a Docker container for Telegraf

3.1 Creating the configuration directory

sudo mkdir -p /opt/telegraf

This command creates the directory /opt/telegraf if it does not already exist. The -p flag ensures that parent directories are also created if needed.

3.2 Creating or editing the configuration file

sudo nano /opt/telegraf/telegraf.conf

sudo is used because the /opt directory may require administrator privileges. In the nano editor the file is saved with Ctrl + O, Enter and closed with Ctrl + X.

3.3 Starting the Telegraf container

docker run -d --name telegraf \
  -v /opt/telegraf/telegraf.conf:/etc/telegraf/telegraf.conf:ro \
  telegraf:latest
ParameterMeaning
docker runCreates and starts a new Docker container.
-dStarts the container in the background (detached mode).
--name telegrafSets the container name to telegraf.
-vMaps a file from the host into the container.
/opt/telegraf/telegraf.confThe configuration file on the host.
/etc/telegraf/telegraf.confThe configuration file inside the container.
:roRead only – the container can read the file but not modify it.
telegraf:latestThe Telegraf Docker image.

3.4 Checking container status

docker ps -a

The correct status looks like:

telegraf:latest   Up ...   telegraf

3.5 Container logs

docker logs telegraf
docker logs telegraf --tail 50
docker logs -f telegraf

Logs are the most important diagnostic tool. If there is an error in the configuration, Telegraf usually prints it here.

3.6 Removing an old container

docker rm -f telegraf

This command forcibly removes the telegraf container. It does not remove the external file /opt/telegraf/telegraf.conf if it was stored on the host.

4. The telegraf.conf configuration file

4.1 The [agent] section

[agent]
  interval = "10s"
  flush_interval = "10s"
ParameterMeaning
interval = "10s" Telegraf reads values from inputs (e.g. Modbus registers) every 10 seconds.
flush_interval = "10s" Telegraf sends or writes the collected data to output every 10 seconds.

4.2 TOML format

telegraf.conf uses the TOML format. Indentation is not as strict as in Python, but correct brackets, quotes, commas, and block structure are important.

Typical error: bad syntax causes the container to crash or start restarting in a loop.

5. First test via CPU metrics

Before Modbus, we first verified that Telegraf as a container was working. A simple test using [[inputs.cpu]] was used for this. 

[agent]
  interval = "10s"
  flush_interval = "10s"

[[inputs.cpu]]
  percpu = true
  totalcpu = true
  collect_cpu_time = false
  report_active = true

[[outputs.file]]
  files = ["stdout"]
  data_format = "influx"
ParameterMeaning
[[inputs.cpu]]Input plugin that collects CPU metrics.
percpu = trueCollects metrics for individual CPU cores.
totalcpu = trueAlso collects the overall CPU summary value.
report_active = trueAlso reports active CPU utilization.
[[outputs.file]]Output plugin that writes data to a file or stdout.
files = ["stdout"]Data is written to standard output, visible via docker logs.
data_format = "influx"Data is in Influx line protocol format.
When lines starting with cpu,... appeared in the logs, it confirmed that the container and configuration were working.

6.2 Converting the value to lux

The sensor has a resolution of 0.01 lux. Therefore the raw register value is converted as follows: 

lux = raw_value * 0.01

Example:

raw = 43712
lux = 43712 * 0.01 = 437.12 lux

6.3 First sensor

[[inputs.modbus]]
  name = "roof_light_sensor_1"
  controller = "tcp://192.168.50.128:4196"
  slave_id = 1

  input_registers = [
    { name = "lux", byte_order = "AB", data_type = "UINT16", scale = 0.01, address = [0] }
  ]

6.4 Second sensor

ParameterMeaning

7. Connecting Telegraf to Mosquitto MQTT Broker

After verifying that ZLAN device values could be read via Modbus TCP, we added an output to the Mosquitto MQTT broker. The broker runs in a Docker container and is available at 192.168.50.103 on port 1883.

SettingValue

Port1883

Topic sensor 2roof_light_sensor_2
Payload{"name":"roof_light_sensor_1","value":461,"unit":"lux"}

7.1 Publishing to topic by sensor name

Each Modbus block has its own name parameter. Telegraf uses it in the metric as the name tag. The MQTT output can therefore use this tag as the topic name: 

topic = '{{ .Tag "name" }}'

The resulting topics in MQTT Explorer are:

roof_light_sensor_1
roof_light_sensor_2

7.2 Required MQTT message format

The goal was not to send the full Telegraf JSON with fields, tags and timestamp, but a simple message: 

{
  "name": "roof_light_sensor_1",
  "value": 461,
  "unit": "lux"
}
The notation "value": 461 "lux" is not valid JSON. The correct approach is to have value and unit separately: "value": 461 and "unit": "lux".

7.3 Why use data_format = "template"

When trying data_format = "json", the full standard Telegraf JSON appeared in MQTT Explorer: 

{
  "fields": {"lux": 461},
  "name": "modbus",
  "tags": {
    "name": "roof_light_sensor_1",
    "slave_id": "1",
    "type": "input_register"
  },
  "timestamp": 1777028990
}

This worked but was overly verbose. Therefore we used data_format = "template", which lets us compose the exact output JSON ourselves.

Note: json_v2 was not used as the final solution here. For a custom MQTT payload we used template.

7.4 Final MQTT output block

[[outputs.mqtt]]
  servers = ["tcp://192.168.50.103:1883"]
  topic = '{{ .Tag "name" }}'
  data_format = "template"
  template = '{"name":"{{ .Tag "name" }}","value":{{ .Field "lux" }},"unit":"lux"}'

7.5 Parameter explanations

ParameterMeaning
[[outputs.mqtt]] Telegraf output plugin that publishes data to an MQTT broker.
servers = ["tcp://192.168.50.103:1883"] Address of the Mosquitto broker.
topic = '{{ .Tag "name" }}' Topic is constructed from the name tag, i.e. the sensor name.
data_format = "template" Enables a custom template for the output message.
{{ .Tag "name" }} Inserts the sensor name, e.g. roof_light_sensor_1.
{{ .Field "lux" }} Inserts the value of the lux field.
"unit":"lux" Adds a fixed unit of measurement to the message.

8. Connecting Telegraf to InfluxDB

After setting up the MQTT output, we also added data sending to InfluxDB. InfluxDB is a database optimized for time series, meaning data that changes over time. It is suitable for light sensors, temperatures, humidity, energy consumption, and other measurements.

SettingValue
InfluxDB addresshttp://192.168.50.103:8086
OrganizationHomeAutomation
BucketRoof_Light_Sensors
Authentication methodAPI Token
Telegraf output plugin[[outputs.influxdb_v2]]

8.1 Why API Token is used in InfluxDB 2.x

In InfluxDB 2.x, an API Token is the standard authentication method for applications and services such as Telegraf. Classic username and password is mainly used for logging into the InfluxDB web interface.

Telegraf is an automated service. It is therefore better to use an API Token with precisely configured permissions, such as write-only access to one bucket. This is more secure than storing administrator credentials.

8.2 What is Organization

An Organization is a logical organizational unit in InfluxDB. It groups buckets, tokens, users, and settings. This project uses: 

HomeAutomation

In telegraf.conf, the organization must be specified exactly as it was created in InfluxDB.

8.3 What is a Bucket

A Bucket is where InfluxDB stores time-series data. It can be thought of as a database or container for a specific type of measurements. This project uses: 

Roof_Light_Sensors

Values from the rooftop light sensors are stored in this bucket.

8.4 What is an API Token

An API Token is a secret key with which Telegraf authenticates to InfluxDB. The token defines what Telegraf is allowed to do. For this project it only needs write access to the Roof_Light_Sensors bucket.

An API Token is sensitive data. Do not share it publicly and do not include it in full in documentation. In this documentation we use the placeholder text SEM_VLOZ_TVOJ_API_TOKEN.

8.5 How to create an API Token in InfluxDB

  1. Open InfluxDB: http://192.168.50.103:8086
  2. Log in to InfluxDB.
  3. Go to Load Data.
  4. Select API Tokens.
  5. Click Generate API Token.
  6. Select Custom API Token.
  7. Select bucket Roof_Light_Sensors.
  8. Set at minimum the Write permission.
  9. Copy the token and store it securely.
The token is often only shown once when created. If you lose it, create a new token.

8.6 Why Write permission is sufficient

Telegraf needs to write data to InfluxDB. It does not need to read historical values, delete data, or manage the database. Therefore it is safer to create a token with only Write permission for the specific bucket.

8.7 Adjusting measurement for cleaner graphs

Without adjustment, data from the Modbus plugin could be stored under the measurement name modbus. This works but for graphs it is cleaner to have a custom name: 

roof_light

Therefore we added the following to each [[inputs.modbus]] block: 

name_override = "roof_light"

The result in InfluxDB will be:

Fieldlux
Tagname=roof_light_sensor_1 or name=roof_light_sensor_2

11. Troubleshooting – real errors and solutions

11.1 Container is in Restarting state

This means the container starts but the main process inside it crashes. Docker then repeatedly attempts to restart it.

Diagnosis:

docker logs telegraf

Most common cause: error in telegraf.conf.

11.2 Permission denied

The user does not have permission to write to the file or directory.

Solution:

sudo nano /opt/telegraf/telegraf.conf

Or check permissions:

ls -l /opt/telegraf/telegraf.conf

11.3 invalid TOML syntax

Syntax error in the configuration file.

Check especially:

  • square brackets [ ],
  • quotes " ",
  • commas in inline objects,
  • correct block names, e.g. [[inputs.modbus]].

11.4 invalid scale '0.000000'

The scale parameter was missing or had an invalid value.

Working solution for lux:

scale = 0.01

For a raw test you can use:

scale = 1.0

11.5 cannot unmarshal TOML integer into []uint16

In this version of the Telegraf Modbus plugin the address parameter expects an array, not a plain number.

Wrong:

address = 0

Correct:

address = [0]

11.6 invalid byte order "ABCD"

For a single 16-bit register, ABCD was an incorrect value.

Correct:

byte_order = "AB"

11.7 invalid byte order ""

The byte_order parameter was empty or incorrectly removed.

Solution:

byte_order = "AB"

11.8 Logs show lines with 0 request(s)

Example:

Got 0 request(s) touching 0 holding registers
Got 0 request(s) touching 0 discrete registers
Got 0 request(s) touching 0 coil registers
This is not an error. It simply means you are not using holding registers, discrete inputs, or coils. You are only using input_registers, so Telegraf correctly reads only those.

11.9 No lux values visible

Steps:

  1. Check that the container is Up: docker ps -a
  2. View logs: docker logs telegraf --tail 100
  3. Check the IP address of the ZLAN device.
  4. Check port 4196.
  5. Check slave_id = 1.
  6. Verify communication in QModMaster.

11.10 MQTT payload contains fields/tags/timestamp

This means standard JSON output is being used instead of a custom template.

Solution:

data_format = "template"
template = '{"name":"{{ .Tag "name" }}","value":{{ .Field "lux" }},"unit":"lux"}'

11.11 MQTT topic is not the sensor name

Check that the MQTT output has: 

topic = '{{ .Tag "name" }}'

11.12 No data visible in MQTT Explorer

  1. Check that the Mosquitto container is running.
  2. Check IP address 192.168.50.103.
  3. Check port 1883.
  4. Check Telegraf logs: docker logs telegraf --tail 100.
  5. Check that the Telegraf container can reach the broker over the network.

11.13 InfluxDB: unauthorized

Telegraf cannot authorize with InfluxDB.

Most commonly caused by an incorrect API Token or a token without write permission for the bucket. Create a new Custom API Token with Write permission for bucket Roof_Light_Sensors.

11.14 InfluxDB: measurement roof_light not visible

Check that both Modbus blocks contain:

name_override = "roof_light"

11.15 InfluxDB: connection refused

Check that the InfluxDB container is running, that port 8086 is accessible, and that the address is correct: 

http://192.168.50.103:8086
