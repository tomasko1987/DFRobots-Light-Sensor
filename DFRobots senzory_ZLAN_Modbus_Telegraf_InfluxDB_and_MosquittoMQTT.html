DFRobots senzory -> ZLAN -> Modbus -> Telegraf -> InfluxDB, Mosquitto MQTT

Táto dokumentácia spája pôvodný návod k vytvoreniu Docker kontajnera pre Telegraf a novšiu dokumentáciu k pripojeniu dvoch ZLAN zariadení s RS485 svetelnými senzormi DFRobot. Je zostavená ako praktický pracovný návod krok po kroku.

Aktuálny cieľ systému:
Dva svetelné senzory DFRobot SEN0644 sú pripojené cez RS485 do dvoch ZLAN prevodníkov. ZLAN zariadenia prevádzajú komunikáciu na Modbus TCP. Telegraf bežiaci v Docker kontajneri tieto hodnoty číta, publikuje ich do MQTT Mosquitto brokera na adrese 192.168.50.103:1883 a zároveň ich vie ukladať do InfluxDB na adrese 192.168.50.103:8086.

1. Architektúra systému a vizuálny diagram

Dátová cesta je:

DFRobot SEN0644 → RS485 → ZLAN 7110M → Modbus TCP → Telegraf Docker kontajner → MQTT Mosquitto + InfluxDB
Doplnenie diagramu: Telegraf má teraz dva výstupy naraz: publikuje aktuálne hodnoty do Mosquitto MQTT a zároveň zapisuje časové dáta do InfluxDB, kde sa ukladajú do bucketu Roof_Light_Sensors.

2. Základné pojmy

2.1 Docker kontajner

Docker kontajner je izolované prostredie, v ktorom beží konkrétna aplikácia. V tomto projekte beží v kontajneri aplikácia Telegraf. Kontajner môže používať vlastné súbory, ale aj súbory z hostiteľského systému cez mapovanie volume.

2.2 Adresár /etc

/etc je v Linuxe štandardné miesto pre konfiguračné súbory programov. Telegraf vo vnútri kontajnera očakáva konfiguráciu typicky tu: 

/etc/telegraf/telegraf.conf

2.3 Adresár /opt

/opt sa často používa pre vlastné aplikácie, pomocné súbory alebo projektové konfigurácie. V tomto prípade máme konfiguračný súbor na hostiteľovi: 

/opt/telegraf/telegraf.conf

2.4 Hostiteľský súbor verzus súbor v kontajneri

Pri spustení kontajnera sme namapovali hostiteľský súbor do kontajnera. To znamená, že Telegraf vo vnútri kontajnera číta /etc/telegraf/telegraf.conf, ale v skutočnosti ide o súbor z hostiteľa: /opt/telegraf/telegraf.conf.

Výhoda: keď sa kontajner zmaže, externý konfiguračný súbor na hostiteľovi sa nezmaže.

3. Vytvorenie Docker kontajnera pre Telegraf

3.1 Vytvorenie priečinka pre konfiguráciu

sudo mkdir -p /opt/telegraf

Príkaz vytvorí priečinok /opt/telegraf, ak ešte neexistuje. Parameter -p zabezpečí, že sa vytvorí aj nadradená cesta, ak treba.

3.2 Vytvorenie alebo úprava konfiguračného súboru

sudo nano /opt/telegraf/telegraf.conf

sudo použijeme preto, že priečinok /opt môže vyžadovať administrátorské práva. V editore nano sa súbor uloží cez Ctrl + O, Enter a zatvorí cez Ctrl + X.

3.3 Spustenie Telegraf kontajnera

docker run -d --name telegraf \
  -v /opt/telegraf/telegraf.conf:/etc/telegraf/telegraf.conf:ro \
  telegraf:latest
ParameterVýznam
docker runVytvorí a spustí nový Docker kontajner.
-dSpustí kontajner na pozadí.
--name telegrafNastaví názov kontajnera na telegraf.
-vNamapuje súbor z hostiteľa do kontajnera.
/opt/telegraf/telegraf.confKonfiguračný súbor na hostiteľovi.
/etc/telegraf/telegraf.confKonfiguračný súbor vo vnútri kontajnera.
:roRead only – kontajner môže súbor čítať, ale nie upravovať.
telegraf:latestDocker image Telegrafu.

3.4 Kontrola stavu kontajnera

docker ps -a

Správny stav je napríklad:

telegraf:latest   Up ...   telegraf

3.5 Logy kontajnera

docker logs telegraf
docker logs telegraf --tail 50
docker logs -f telegraf

Logy sú najdôležitejší nástroj pri diagnostike. Ak je chyba v konfigurácii, Telegraf ju väčšinou vypíše práve sem.

3.6 Odstránenie starého kontajnera

docker rm -f telegraf

Tento príkaz vynútene zmaže kontajner telegraf. Nezmaže však externý súbor /opt/telegraf/telegraf.conf, ak bol uložený na hostiteľovi.

4. Konfiguračný súbor telegraf.conf

4.1 Sekcia [agent]

[agent]
  interval = "10s"
  flush_interval = "10s"
ParameterVýznam
interval = "10s" Telegraf každých 10 sekúnd načíta hodnoty zo vstupov, napríklad Modbus registrov.
flush_interval = "10s" Telegraf každých 10 sekúnd odošle alebo vypíše nazbierané dáta na výstup.

4.2 TOML zápis

telegraf.conf používa formát TOML. Odsadenie nie je také prísne ako v Pythone, ale dôležité sú správne zátvorky, úvodzovky, čiarky a štruktúra blokov.

Typická chyba: zlá syntax spôsobí, že kontajner spadne alebo sa začne reštartovať.

5. Prvý test cez CPU metriky

Pred Modbusom sme najprv overili, že Telegraf ako kontajner funguje. Na to bol použitý jednoduchý test cez [[inputs.cpu]]. 

[agent]
  interval = "10s"
  flush_interval = "10s"

[[inputs.cpu]]
  percpu = true
  totalcpu = true
  collect_cpu_time = false
  report_active = true

[[outputs.file]]
  files = ["stdout"]
  data_format = "influx"
ParameterVýznam
[[inputs.cpu]]Vstupný plugin, ktorý zbiera CPU metriky.
percpu = trueZbiera metriky pre jednotlivé CPU jadrá.
totalcpu = trueZbiera aj súhrnnú hodnotu CPU.
report_active = trueVypisuje aj aktívne využitie CPU.
[[outputs.file]]Výstupný plugin, ktorý dáta vypíše do súboru alebo na stdout.
files = ["stdout"]Dáta sa vypisujú do štandardného výstupu, teda ich vidno cez docker logs.
data_format = "influx"Dáta sú vo formáte Influx line protocol.
Keď sa v logoch objavili riadky začínajúce cpu,..., znamenalo to, že kontajner aj konfigurácia fungujú.

6.2 Prevod hodnoty na lux

Senzor má rozlíšenie 0.01 lux. Preto sa raw hodnota z registra prepočíta takto: 

lux = raw_hodnota * 0.01

Príklad:

raw = 43712
lux = 43712 * 0.01 = 437.12 lux

7. Napojenie Telegrafu na Mosquitto MQTT Broker

Po overení čítania hodnôt zo ZLAN zariadení cez Modbus TCP sme doplnili výstup do MQTT brokera Mosquitto. Broker beží v Docker kontajneri a je dostupný na adrese 192.168.50.103 na porte 1883.

NastavenieHodnota
MQTT brokerMosquitto v Docker kontajneri
IP adresa192.168.50.103
Port1883
Topic senzora 1roof_light_sensor_1
Topic senzora 2roof_light_sensor_2
Payload{"name":"roof_light_sensor_1","value":461,"unit":"lux"}

7.1 Publikovanie do topicu podľa názvu senzora

Každý Modbus blok má vlastný parameter name. Telegraf ho v metrike používa ako tag name. Preto môže MQTT výstup použiť tento tag aj ako názov topicu: 

topic = '{{ .Tag "name" }}'

Výsledné topicy v MQTT Exploreri sú:

roof_light_sensor_1
roof_light_sensor_2

7.2 Požadovaný formát MQTT správy

Cieľom bolo neposielať plný Telegraf JSON s fields, tags a timestamp, ale jednoduchú správu: 

{
  "name": "roof_light_sensor_1",
  "value": 461,
  "unit": "lux"
}
Zápis "value": 461 "lux" nie je validný JSON. Správne je mať hodnotu a jednotku oddelene: "value": 461 a "unit": "lux".

7.3 Prečo použiť data_format = "template"

Pri pokuse o data_format = "json" sa v MQTT Exploreri zobrazoval celý štandardný Telegraf JSON: 

{
  "fields": {"lux": 461},
  "name": "modbus",
  "tags": {
    "name": "roof_light_sensor_1",
    "slave_id": "1",
    "type": "input_register"
  },
  "timestamp": 1777028990
}

To bolo funkčné, ale príliš ukecané. Preto sme použili data_format = "template", kde si presne vyskladáme výsledný JSON.

Pozor: json_v2 sa tu nepoužil ako finálne riešenie. Pre vlastný MQTT payload sme použili template.

7.4 Finálny MQTT output blok

[[outputs.mqtt]]
  servers = ["tcp://192.168.50.103:1883"]
  topic = '{{ .Tag "name" }}'
  data_format = "template"
  template = '{"name":"{{ .Tag "name" }}","value":{{ .Field "lux" }},"unit":"lux"}'

8. Napojenie Telegrafu na InfluxDB

Po nastavení MQTT výstupu sme doplnili aj odosielanie dát do InfluxDB. InfluxDB je databáza optimalizovaná na časové rady, teda na dáta, ktoré sa menia v čase. Hodí sa napríklad na svetelné senzory, teploty, vlhkosti, spotrebu energie alebo iné merania.

NastavenieHodnota
InfluxDB adresahttp://192.168.50.103:8086
OrganizationHomeAutomation
BucketRoof_Light_Sensors
Spôsob autentifikácieAPI Token
Telegraf output plugin[[outputs.influxdb_v2]]

8.1 Prečo sa v InfluxDB 2.x používa API Token

V InfluxDB 2.x sa pre aplikácie a služby, ako je Telegraf, štandardne používa API Token. Klasické meno a heslo slúži hlavne na prihlásenie používateľa do webového rozhrania InfluxDB.

Telegraf je automatická služba. Preto je lepšie použiť API Token, ktorý má presne nastavené práva, napríklad iba zápis do jedného bucketu. Je to bezpečnejšie ako ukladať administrátorské meno a heslo.

8.2 Čo je Organization

Organization je logická organizačná jednotka v InfluxDB. Združuje buckety, tokeny, používateľov a nastavenia. V tomto projekte používame: 

HomeAutomation

V telegraf.conf musí byť organization zadaná presne tak, ako je vytvorená v InfluxDB.

8.3 Čo je Bucket

Bucket je miesto, kam InfluxDB ukladá časové dáta. Dá sa predstaviť ako databáza alebo kontajner pre konkrétny typ meraní. V tomto projekte používame: 

Roof_Light_Sensors

Do tohto bucketu sa ukladajú hodnoty zo strešných svetelných senzorov.

8.4 Čo je API Token

API Token je tajný kľúč, ktorým sa Telegraf autentifikuje voči InfluxDB. Token určuje, čo môže Telegraf robiť. Pre tento projekt mu stačí právo zapisovať do bucketu Roof_Light_Sensors.

API Token je citlivý údaj. Neposielaj ho verejne a nedávaj ho do dokumentácie v plnom znení. V dokumentácii používame zástupný text SEM_VLOZ_TVOJ_API_TOKEN.

8.5 Ako vytvoriť API Token v InfluxDB

  1. Otvor InfluxDB: http://192.168.50.103:8086
  2. Prihlás sa do InfluxDB.
  3. Choď do časti Load Data.
  4. Vyber API Tokens.
  5. Klikni na Generate API Token.
  6. Vyber Custom API Token.
  7. Vyber bucket Roof_Light_Sensors.
  8. Nastav minimálne právo Write.
  9. Token skopíruj a bezpečne ulož.
Token sa často zobrazí iba raz pri vytvorení. Ak ho stratíš, vytvor nový token.

8.6 Prečo stačí právo Write

Telegraf potrebuje do InfluxDB zapisovať dáta. Nepotrebuje čítať historické hodnoty, mazať dáta ani spravovať databázu. Preto je bezpečnejšie vytvoriť token iba s právom Write do konkrétneho bucketu.

8.7 Úprava measurement pre krajšie grafy

Bez úpravy by sa dáta z Modbus pluginu mohli ukladať pod measurement modbus. To funguje, ale pre grafy je krajšie mať vlastný názov:

name_override = "roof_light"

11. Troubleshooting – reálne chyby a riešenia

9.1 Kontajner je v stave Restarting

Znamená to, že kontajner sa spustí, ale hlavný proces v ňom spadne. Docker sa ho potom pokúša opakovane spúšťať.

Diagnostika:

docker logs telegraf

Najčastejšia príčina: chyba v telegraf.conf.

9.2 Permission denied

Používateľ nemá práva zapisovať do súboru alebo priečinka.

Riešenie:

sudo nano /opt/telegraf/telegraf.conf

Prípadne skontrolovať práva:

ls -l /opt/telegraf/telegraf.conf

9.3 invalid TOML syntax

Chyba syntaxe v konfiguračnom súbore.

Kontroluj hlavne:

  • hranaté zátvorky [ ],
  • úvodzovky " ",
  • čiarky v inline objektoch,
  • správne názvy blokov, napríklad [[inputs.modbus]].

9.4 invalid scale '0.000000'

Parameter scale chýbal alebo mal neplatnú hodnotu.

Funkčné riešenie pre lux:

scale = 0.01

Pre raw test je možné použiť:

scale = 1.0

9.5 cannot unmarshal TOML integer into []uint16

V tejto verzii Telegraf Modbus pluginu parameter address očakáva pole, nie obyčajné číslo.

Nesprávne:

address = 0

Správne:

address = [0]

9.6 invalid byte order "ABCD"

Pri jednom 16-bit registri bola hodnota ABCD nesprávna.

Správne:

byte_order = "AB"

9.7 invalid byte order ""

Parameter byte_order bol prázdny alebo zle odstránený.

Riešenie:

byte_order = "AB"

9.8 Logy ukazujú riadky s 0 request(s)

Príklad:

Got 0 request(s) touching 0 holding registers
Got 0 request(s) touching 0 discrete registers
Got 0 request(s) touching 0 coil registers
Toto nie je chyba. Znamená to len, že nepoužívaš holding registre, discrete inputy ani coils. Používaš iba input_registers, takže Telegraf správne číta len tie.

9.9 Nevidím hodnoty lux

Postup:

  1. Skontroluj, či je kontajner Up: docker ps -a
  2. Pozri logy: docker logs telegraf --tail 100
  3. Skontroluj IP adresu ZLAN zariadenia.
  4. Skontroluj port 4196.
  5. Skontroluj slave_id = 1.
  6. Over komunikáciu v QModMasteri.

9.10 MQTT payload obsahuje fields/tags/timestamp

To znamená, že sa používa štandardný JSON výstup namiesto vlastnej šablóny.

Riešenie:

data_format = "template"
template = '{"name":"{{ .Tag "name" }}","value":{{ .Field "lux" }},"unit":"lux"}'

9.11 MQTT topic nie je názov senzora

Skontroluj, či je v MQTT výstupe nastavené: 

topic = '{{ .Tag "name" }}'

9.12 Nevidno dáta v MQTT Exploreri

  1. Skontroluj, či beží Mosquitto kontajner.
  2. Skontroluj IP adresu 192.168.50.103.
  3. Skontroluj port 1883.
  4. Skontroluj logy Telegrafu: docker logs telegraf --tail 100.
  5. Skontroluj, či Telegraf kontajner vie sieťovo dosiahnuť broker.

11.13 InfluxDB: unauthorized

Telegraf sa nevie autorizovať voči InfluxDB.

Najčastejšie ide o nesprávny API Token alebo token bez práva zapisovať do bucketu. Vytvor nový Custom API Token s právom Write pre bucket Roof_Light_Sensors.

11.14 InfluxDB: nevidím measurement roof_light

Skontroluj, či je v oboch Modbus blokoch:

name_override = "roof_light"

11.15 InfluxDB: connection refused

Skontroluj, či InfluxDB kontajner beží, či je dostupný port 8086 a či je správna adresa: 

http://192.168.50.103:8086

12. Ďalšie možné rozšírenia

12.1 MQTT Mosquitto výstup

MQTT výstup je už zapracovaný v sekcii 7. Používa broker 192.168.50.103:1883, topic podľa názvu senzora a vlastný JSON payload cez data_format = "template".

12.2 InfluxDB a Grafana

InfluxDB výstup je už zapracovaný v sekcii 8. Ďalším krokom môže byť Grafana, ktorá vie z bucketu Roof_Light_Sensors kresliť grafy pre senzory roof_light_sensor_1 a roof_light_sensor_2.

12.3 Home Assistant

Ak budú dáta publikované do MQTT, Home Assistant ich môže načítať ako MQTT senzory.
